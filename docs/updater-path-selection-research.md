# 更新下載的選路量測：問題、根因、修正

> 起因：使用者回報「我的 SOCKS5 能跑到 400 Mbps+，但自動更新每次都選不到那條，
> 好像都走不到 100 Mbps 的 PPPoE 線路」。
>
> 調查日期：2026-10-03。結論：**不是一個問題，是一串獨立缺陷疊在一起**
> （D1~D9），其中兩個讓「代理」這條候選從來沒有真正參與過比較。
>
> 後續（同日）：使用者追加問「有沒有能自己判斷怎麼下載才快的技術」，
> 於是量了「並行度到底有沒有用」（§5 更正 3），並實作了**自適應連線數**
> （§8，預設關閉）。

---

## 1. 環境拓撲（實測，非推測）

| 項目 | 實測值 | 來源 |
|---|---|---|
| PC 實體網卡 | `乙太網路` Intel I211，`192.168.1.200/24`，LinkSpeed 1 Gbps | `Get-NetAdapter` |
| 預設閘道 | `192.168.1.2`（路由器），InterfaceMetric=1 | `Get-NetRoute` |
| PPPoE | **PC 上沒有 PPPoE 網卡** —— 由路由器撥號 | `Get-NetAdapter` 清單無 PPPoE |
| SOCKS5 代理 | `192.168.1.178:1080`（手機，5G Proxy Pro），與 PC 同一個 LAN | `config.json` |
| 手機 5G 自身速度 | 下載 440.43 Mbps / PING 15 ms（台灣大哥大） | 使用者提供的 Speedtest 截圖 |
| 引擎規則 | 1 條：`type=Name, target='*', action=PROXY (轉發)` = **全局轉發** | `config.json` |

**關鍵事實：這台 PC 沒有 PPPoE 網卡。** 所以「直連」不是一條網卡，
而是「走作業系統預設路由 → 路由器 → PPPoE」。這決定了下面的判別方法。

### 判別法：比對出口 IP

這是整份調查裡最便宜也最決定性的一招 —— 不需要拆線、不需要停引擎：

```
引擎運行中：  不指定代理 -> 49.215.44.84
              經手機代理 -> 49.215.44.84      ← 完全相同

引擎停止後：  不指定代理 -> 220.134.135.193   （中華電信 PPPoE）
              經手機代理 -> 49.215.44.84      （台灣大哥大 5G）
```

**出口 IP 相同 ⇒ 兩條候選路是同一條實體線。** 這一條判據直接推翻了本報告
初稿的一個結論（見 §5）。

## 2. 缺陷清單

### D1（硬性）`PySocks` 沒裝 → SOCKS5 從來沒進過候選

`updater.py` 用 `requests` + `socks5h://` 走代理，但 `requests` 需要 `PySocks`
才認得這個 scheme：

```
>>> requests.get('https://api.github.com/', proxies={'https':'socks5h://192.168.1.178:1080'})
requests.exceptions.InvalidSchema: Missing dependencies for SOCKS support.
```

`requirements.txt` 只有 `PySide6` / `requests`；`.venv` 與 `IntegratedApp.dist`
都沒有 `socks` 模組。CI 是 `pip install -r requirements-dev.txt`（內含
`-r requirements.txt`），所以**建置環境也從來沒有它 —— 已發佈的每個版本，
更新器裡的 SOCKS5 通路都是死的**。

而 `_measure_path` 的 `except Exception` 把它吞了：

```
_measure_path(直連)                     -> 20188 B/s
_measure_path(socks5h://192.168.1.178)  -> None，耗時 0.00 秒   ← 0.00 秒 = 拋例外，不是逾時
_rank_download_paths()                  -> [(None, 33618.0, '直連')]  ← 代理不在候選裡
```

> 對照組：`MultiSocksDownloader/requirements.txt` **有** `PySocks==1.7.1`。
> 同一個作者、同一套設計，只有 NetRedirector 漏了這一項。

### D2（方法論）探針量的是延遲，不是吞吐

`PROXY_PROBE_BYTES = 256 KB`，且計時從**發起請求前**起算，所以
`got / dt` 的分母是「連線 + TLS + GitHub 302 轉址 + TTFB + 傳輸」。
用真實資產（34 MB zip）實測兩者：

| 路徑 | 舊法（256 KB） | 穩態法（4 MB，從首字節起算） |
|---|---|---|
| 直連 | 1.1 Mbps | **119.4 Mbps** |
| MyPhone SOCKS5 | 1.3 Mbps | **79.5 Mbps** |

**低估約 100 倍。** 原因可以算出來：curl 量到 GitHub 資產的 TTFB 中位數是
**976.8 ms**，而 256 KB 在 300 Mbps 上只帶 **21 ms** —— 分母有 98% 是延遲。
把實測 TTFB 代回去：即使代理真跑到 400 Mbps，探針值仍是 0.169 MB/s，
低於直連的 0.232 MB/s；**要讓那條 400 Mbps 的代理被選中，直連得慢到 5 Mbps 以下。**

### D3（乘法效應）1 MB 分段 × 每請求 ~1.3 秒延遲

`TARGET_BLOCK_SIZE = 1 MB` / `MAX_BLOCKS = 32`，34 MB 的檔被切成 32 段。
給 `_fetch_block` 加計時後，每段的時間組成是：

| 階段 | 直連 | MyPhone |
|---|---|---|
| `t_req`：發出 → 回應標頭 | **1265.5 ms** | **1726.0 ms** |
| `t_first`：標頭 → 首個 chunk | 422.0 ms | 367.5 ms |
| `t_read`：首 chunk → 讀完 | 328.0 ms | 195.0 ms |

**真正搬資料只有 195~328 ms，其餘都在等回應。** 段數掃描（引擎運行中）：

| 設定 | 直連 | MyPhone |
|---|---|---|
| 32 段 × 1.0 MB（修正前） | 65.2 Mbps | **Read timed out** |
| 16 段 × 2.0 MB | 84.7 | 71.0 |
| 8 段 × 4.1 MB | 93.4 | 70.0 |
| 4 段 × 8.2 MB | **107.7** | **74.9** |
| 2 段 × 16.3 MB | 107.7 | 69.1 |
| 1 段 × 32.7 MB | 107.2 | 80.1 |

2×2 對照（curl，同一目標，`-L` 跟隨轉址，統計真實 `size_download`）：

| 組合 | Mbps |
|---|---|
| 8 併發 · 完整檔 | 304.2 |
| 8 併發 · 1 MB Range | 43.5 |
| 32 併發 · 完整檔 | 404.8 |
| 32 併發 · 1 MB Range | 111.7 |

→ **罪魁是 1 MB 的 Range 請求，不是併發數。** 完整檔下載時併發越多越快；
改成 1 MB 分段後反而慢了 3~7 倍。

### D4（程式缺陷）`DOWNLOAD_THREADS` 被完全忽略

```python
def _download_multipart(final_url, dest, total, threads, progress_cb, ...):
    ...
    n = len(bounds)
    workers = [threading.Thread(target=worker, daemon=True) for _ in range(n)]
```

在函式體內 grep `threads` **零命中** —— 參數存在但從未使用，worker 執行緒數
直接等於段數。34 MB 的檔會開 **32 條連線**，`DOWNLOAD_THREADS = 8` 是裝飾品。

兩個獨立證據：
1. 1 緒與 8 緒的結果幾乎相同（75.0 vs 69.6 Mbps）—— 若參數有效不可能如此。
2. 內部計時的「重疊度」= Σ各段佔用 / 牆鐘 = **19.23**，在 8 條執行緒下
   數學上不可能。

### D5（靜默）失敗不發聲

`_measure_path` 把所有例外吞成 `None`，呼叫端只看到「這條路沒分數」。
於是「代理一直沒被選上」看不出來是代理掛了、逾時了、還是程式根本沒把
SOCKS 送出去 —— D1 就是靠這個藏了整個產品生命週期。

### D6（標籤說謊）引擎全局轉發時，「直連」不是直連

`_rank_download_paths` 把「不指定代理」那條候選標成 `"直連"`。但引擎規則
是 `target='*'` 的全局轉發時，這條路徑同樣被 WinDivert 攔下來轉到同一個
代理 —— 出口 IP 實測完全相同。使用者看到日誌寫「直連」，
自然以為下載走的是 PPPoE 實體線。

### D7（誤殺）小於約 3.5 MB 的資產，快路徑會被全部判成「樣本不足」

探針的 `Range` 是 `bytes=0-(8 MB - 1)`，但守則是「量測視窗短於 0.3 秒
= 樣本不足，丟棄」。當**檔案本身就小於「0.3 秒能抓完的量」**時，伺服器會
把整份送完、串流自然結束 —— 既沒撞到 8 MB 上限，視窗又短於 0.3 秒，
於是被判「樣本不足」。**整份檔案都抓完了，卻被當成「量不出來」。**

在 95 Mbps 的直連上實測（`exp13_short_sample.py`）：

| 檔案 | 實抓 | 量測視窗 | 修正前 | 修正後 |
|---|---|---|---|---|
| 0.25 MB | 0.25 | 0.000 s | **丟棄：樣本不足** | OK 7.5 Mbps |
| 0.50 MB | 0.50 | 0.016 s | **丟棄** | OK 12.7 Mbps |
| 1.00 MB | 1.00 | 0.078 s | **丟棄** | OK 22.4 Mbps |
| 2.00 MB | 2.00 | 0.156 s | **丟棄** | OK 33.6 Mbps |
| 4.00 MB | 4.00 | 0.344 s | OK 97.5 Mbps | OK 52.4 Mbps |
| 8.00 MB | 8.00 | 0.719 s | OK 93.3 Mbps | OK 66.1 Mbps |

後果：所有快路徑一起被丟掉，`_rank_download_paths` 只剩 `speed=0.0` 的直連
保底 → **代理永遠選不上**。這是使用者原始抱怨的另一個成因。
NetRedirector 的更新檔是 34 MB 所以踩不到，但**下載器專案只要抓小檔就會踩到**。

### D8（重複付費）同一條路徑被探測兩次

選路階段已經對每條候選發過一次帶 `Range` 的請求、也跟完了轉址、拿到了
`content-range`。但 `_download_over_path` 又無條件呼叫 `_probe_download`
（`Range: bytes=0-0`），**再付一次完整 TTFB**。實測那一次要 1.7~2.1 秒，
佔 34 MB 資產牆鐘時間的 36~48%（見 §6.5）。

### D9（宣告與行為不一致）伺服器宣告 `Accept-Ranges: bytes` 卻對任何 Range 回 416

`http.speed.hinet.net`（HTTP/80，`Server: HiNet`）實測：`Range: bytes=0-0` /
`bytes=0-` / `bytes=0-1023` / 中段 / 大段 —— **全部回 416**，與 HTTP 版本、
User-Agent 無關；但它的回應標頭仍寫 `Accept-Ranges: bytes`。同一個 host 的
**HTTPS/443 是好的**（`Server: nginx/1.30.2`，Range → 206）。

引擎因此**完全無法下載**（探針硬要 Range）：
```
_probe_download        → HTTPError 416
_measure_path_detailed → speed=None, error='HTTP 416'
download_file          → RuntimeError: 下載失敗: 416   ← 0.02 秒就死
```
而 curl 抓同一個 URL：40 MB / 3.77~3.88 s / 87~89 Mbps。

**根因**：舊版只處理「伺服器**忽略** Range、回整份 200」這一種
（→ `supports_range=False`），沒處理「伺服器**拒絕** Range、回 4xx」。
`_probe_download` 對 416 直接 `raise_for_status()`，於是
`_download_over_path` 根本**走不到它自己早就寫好的單線備援**
（`_download_single` 不送 Range，其實可用）。

**修法**：新增 `_RANGE_REJECT_CODES = (400, 416, 501)`、`_range_rejected()`、
`_get_allow_range_fallback()` —— 被拒就**拿掉 `Range` 標頭重送一次**，回報
`supports_range=False`，於是自動走單線。這是**通用退路**，不寫死任何 hostname、
也不做 HTTP→HTTPS 升級。修後 `download_file` 成功 **3.74 s / 89.8 Mbps**，
比 curl 的 3.77~3.88 s 還略快。

> 姊妹專案 `MultiSocksDownloader/downloader.py`（它的**主下載引擎**，是另一套
> 程式）早就用**不同**的做法處理同一件事：`_upgrade_http_to_https()` 把
> `http://` 換成 `https://` 重試，註解直接寫「如 HiNet 測速檔」。兩種修法互補：
> HTTPS 升級能保住分段；拿掉 Range 則在沒有 HTTPS 時仍可用。本專案的 updater
> 只抓 GitHub（已是 https），所以只做了後者。

### `updater.py`

| 項目 | 修正前 | 修正後 |
|---|---|---|
| 探針計時 | 從發起請求前起算 | 分兩段：TTFB 不計入分母，只量「首個 chunk 之後」 |
| 探針上限 | 固定 256 KB | 時間預算 1.5 s + 位元組上限 8 MB，撞到上限視為有效樣本 |
| 探針回報 | `float \| None` | `(speed, info)`，`info` 含 `ttfb`/`bytes`/`elapsed`/`error` |
| 分段大小 | 固定 1 MB | 下限 8 MB |
| 分段數上限 | 32 | 8 |
| worker 數 | `= 段數`（忽略 `threads`） | `min(threads, MAX_BLOCKS, ceil(total/MIN_BLOCK_SIZE))` |
| 失敗回報 | 全部吞掉 | 逐條輸出原因（逾時／HTTP 碼／例外型別） |
| 逾時未完成 | 靜默以 0 分墊底 | 明確記錄「量測未在 N 秒內完成」 |
| 候選標籤 | `"直連"` | `"系統路由（未指定代理）"`（`DIRECT_LABEL`） |
| 選路日誌 | 只印被選中的那條 | 印出全部候選與各自速度，由快到慢 |
| 探針回報（續） | — | 另帶 `final_url` / `total` / `supports_range` |
| 選路 → 下載 | 下載前再探一次（多付一次 TTFB） | 沿用選路探針的 `final_url` / `total`，整段省掉 |
| 「樣本不足」判定 | 視窗 < 0.3 s 就丟棄 | 整份抓完（`got >= total`）算完整樣本 |
| 整份抓完時的計速 | —（會被丟棄） | 改用**含 TTFB 的牆鐘**，這才是端到端實感 |
| 被拒絕的 Range（D9） | 直接 `raise_for_status()` → 下載起不來 | `_get_allow_range_fallback()`：拿掉 `Range` 重送，改走單線 |
| 連線數（§8） | 寫死 `DOWNLOAD_THREADS = 8` | `ADAPTIVE_CONCURRENCY`（預設關閉）→ `_adaptive_threads()` 逐次量測決定 |
| 開關來源 | — | `config.json` 頂層 `"adaptive_concurrency"`（`_config_flag`） |

`DIRECT_LABEL` 刻意不叫「直連」：專案裡 `DIRECT (直連)` 已經是引擎規則的
專有名詞，updater 拿它指「不指定代理」本身就是混淆源頭。

## 4. 量測方法（為什麼要這樣量）

1. **用 curl 當獨立協定棧。** curl 原生支援 `socks5h`，不需要 PySocks，
   所以它不受本專案的相依問題污染 —— 在修好 D1 之前，只有它能量到代理。
   對照後也確認 PySocks 本身沒有額外成本：
   `python requests` 完整檔 8 緒 = 直連 303.9 / 代理 285.4 Mbps，
   與 curl 的 304.2 Mbps 一致。
2. **對照組必須分離變因。** D3 的 2×2（併發數 × Range/完整檔）是為了避免
   把「併發懲罰」誤判成「Range 懲罰」。
3. **計時要拆階段。** 只量總耗時無法區分「等回應」與「搬資料」，
   D3 就藏在這個盲點裡。
4. **出口 IP 比對。** 判斷兩條候選路是不是同一條實體線，最便宜的方法。

## 5. 被推翻的推論（更正記錄）

初稿寫過「直連 PPPoE 304 Mbps，所以這條線不只 100 Mbps」。
**這是錯的。** 當時引擎正在全局轉發，「直連」那一臂也被轉到手機 SOCKS5，
量到的是 5G，不是 PPPoE。使用者指出這一點後，用出口 IP 比對證實：

- 引擎運行中，兩臂出口 IP 都是 `49.215.44.84` → 同一條 5G
- 引擎停止後，不指定代理變成 `220.134.135.193` → 才是真的 PPPoE

因此 §2 的 D3 段數掃描、以及 HiNet 上的「304 vs 299」，
**都是 5G 內部的比較（經引擎轉發 vs 直連代理），不是 PPPoE vs 5G。**
段數越少越快的結論不受影響（它量的是同一條 5G 上的引擎行為）。

另外兩件被排除的：
- `MultiSocksDownloader/update_apply_err.log`（17 KB）**不是錯誤日誌** ——
  126 行、0 個 `Traceback`，是檔名誤導。
- 一度懷疑 PySocks 的 Python 層 socket 包裝拖慢代理：**不成立**（見 §4.1）。

**更正 2：「引擎在這條 5G 上的天花板約 78 Mbps」也是錯的框架。**
那是兩個**不同分母**的數字被擺在一起比。`exp9` 的分母從**首個 chunk** 起算
（純穩定態吞吐），`exp10` / `exp11` 從 **t0** 起算（牆鐘，含連線與 TTFB）。
同一個「5 段 × 34 MB」下載，用前者量是 192.9 Mbps、用後者是 78.0 Mbps ——
**2.5 倍差距全部來自分母**，不是 5G 變慢，也不是引擎的吞吐有問題。
把牆鐘拆開之後（§6.5）引擎的穩定態是 **175~319 Mbps**，與 `curl` 的
84.5~122.7 Mbps 同一個量級甚至更高。真正的問題是**固定成本**，不是吞吐。

教訓：**兩個「速度」要放在一起比之前，先確認分母是同一段時間。**
我自己的兩個腳本量同一件事差 2.5 倍，第一反應是「5G 漂移」，
實際上是我的兩支腳本用了不同的計時起點。

**更正 3：更正 2 的結論「引擎穩定態 175~319 Mbps，比 curl 的 84.5~122.7 高」
也是錯的 —— 這次錯在拿「引擎的穩定態」比「curl 的牆鐘」。**

同分母重測（`exp20`，三臂、12 輪、**輪轉順序**、背靠背交錯）：

| 臂 | 中位牆鐘 | 穩定態 Mbps |
|---|---|---|
| curl 單連線 | **2.07 s** | 242.5 |
| curl 8 並行 | 2.39 s | 183.2 |
| 引擎（5 連線） | 3.05 s | 158.1 |

配對差：**引擎 − curl單 = 中位 +0.77 s，curl 12/12 全勝**（p≈0.0002）。
⇒ **使用者最初的觀察（curl 明顯比引擎快）方向是對的**，是我更正過頭了。

**真因是連線數，不是 Python、不是 PySocks、不是 per-chunk 加鎖**
（`exp21`，12 輪連線數掃描）：

| 臂 | 中位牆鐘 | 階段（連線 / 離散 / 傳輸） |
|---|---|---|
| curl 單連線 | 2.38 s | — |
| **引擎 t1** | **2.08 s** | 1.11 / 0.00 / **0.97** |
| 引擎 t2 | 2.77 s | 1.08 / 0.01 / 1.67 |
| 引擎 t4 | 2.86 s | 1.26 / 0.09 / 1.50 |
| 引擎 t8 | 2.92 s | 1.27 / 0.11 / 1.55 |

- **引擎 t1 − curl單 = 中位 +0.05 s，6/12** ⇒ **完全打平**，引擎實作沒問題。
- **1 條連線的傳輸段 0.97 s（282 Mbps）；5 條反而 1.55 s（177 Mbps）**
  ⇒ 這條路**懲罰並行**。
- 連 curl 自己也是：**curl8 − curl單 = 中位 +0.36 s，curl 單 11/12 勝**。

`exp23`（引擎4 / 原始4段 / 引擎1，同場交錯 6 輪）再排除「實作吃掉並行紅利」：
**手寫的原始 4 段（3.89 s / 70.5 Mbps）反而比引擎 4 段（3.05 s / 90.0 Mbps）慢。**
瓶頸就是連線數策略本身。

教訓：**「誰比誰快」的比較，兩個分母都要是同一段時間、同一種定義，而且要在同一場
交錯量。** 我在同一個地方跌了兩次，第二次還是拿自己剛修正的結論去犯。

⇒ 要動它，得先做兩件事：把輪數拉到 ≥10，並在探針裡記下「哪個候選撞到

自適應才補上 `max_blocks`）。

**尚未移植：D5（失敗靜默）與 D6（標籤「直連」說謊）。** 原因很具體：它的
`_rank_download_paths(url, use_proxy=True)` 沒有 `log_cb` 參數，而 D5 要「把失敗
講出來」就得先把日誌介面一路穿進去（選路 → 下載 → 呼叫端），D6 的 `DIRECT_LABEL`
也掛在同一個函式上。所以在補上 `log_cb` 之前，它這兩條維持原狀 —— 不是忘了。

> ⚠️ 更正記錄：本節初稿曾寫成「D2/D3/**D5/D6**/D7/D8/D9 都已同步」，那是錯的。
> 錯因是把「交接文件裡寫了」當成「程式裡做了」，沒有實際 grep 驗證。實際在該檔
> 搜 `log_cb` 與 `DIRECT_LABEL` 是**零命中**。於 2026-10-03 發佈 v1.8.3 時更正。

**其中 D7 對它比對本專案更要緊** —— 下載器抓的是使用者給的任意檔案，
小檔比 34 MB 的更新檔常見得多。可移植的規則：

1. **探針必須把 TTFB 排除在分母外。** 分母含握手時間的探針，量到的是
   `1 / TTFB`，不是吞吐。
2. **探針用時間預算 + 位元組上限，撞到上限算有效樣本。** 讀得快不是壞事。
3. **分段大小下限要跟「每請求固定延遲」掛鉤。** 固定延遲 1.3 秒的 CDN 上，
   1 MB 分段有 98% 的時間在等回應。
4. **`threads` 參數要真的決定 worker 數**，不要用 `len(bounds)`。
   寫個測試斷言「1 緒明顯慢於 8 緒」就能守住這一條。
5. **失敗要發聲**，而且要把「依賴缺失」與「路徑不可用」分開 ——
   前者是程式問題，不該被當成「這條路不好」。
6. **候選路徑的標籤要誠實。** 引擎可能已經改寫了「直連」的語意。
7. **探針要順便把 `final_url` / `total` 帶回給下載階段用。** 同一條路徑
   探兩次，第二次的 TTFB 是白付的（實測 1.7~2.1 秒 = 牆鐘的 36~48%）。
8. **「樣本不足」不能只看時間窗。** 整份抓完就是完整樣本 —— 否則凡是
   小於「0.3 秒 × 線速」（95 Mbps 上約 3.5 MB）的資產，都會讓**所有**
   快路徑一起消失，選路只剩保底的直連。下載器抓小檔時必踩。
9. **整份抓完時，用含 TTFB 的牆鐘計速。** 小檔案用穩定態會反過來高估
   「TTFB 高但吞吐大」的路徑（實測 0.5 MB：穩定態 262 Mbps，
   端到端其實 0.33 秒，比代理的 1.3 秒快）。
10. **「伺服器拒絕 Range」和「伺服器忽略 Range」是兩件事。** 前者回 4xx
    （要拿掉標頭重送，D9），後者回整份 200（`supports_range=False`）。
    只處理後者，遇到前者會**連下載都起不來**。
11. **要比較「多開連線有沒有用」時，聚合量測必須有位元組上限、且每條連線從
    不同偏移起讀。** 少了位元組上限，快路徑會在視窗內把整個檔抓完，量到的
    其實是「檔案大小 ÷ 視窗」。
12. **並行度不是越多越好，也不該寫死。** 決策要靠量測（§8），而且要有
    「試探成本 vs 可能省下的時間」的經濟門檻 —— 檔案太小就別試探。

## 8. 自適應連線數（`ADAPTIVE_CONCURRENCY`，預設關閉）

§5 更正 3 的結論是「這條路懲罰並行」。但那是**這一條**路徑的結論，不是普世真理；
把 `DOWNLOAD_THREADS` 從 8 改成 1 只是把同一個猜測換一個方向。所以改成
**讓程式自己量、自己決定**。

### 8.1 設計

兩個訊號，都**免費**（選路探針已經付過）：

- `bw1 = info["speed"]` —— 單連線的吞吐（`_measure_path_detailed` 現在會把
  回傳的速度一併寫進 `info["speed"]`）。
- `ttfb1 = info["ttfb"]` —— 單連線的連線延遲。

決策（`_adaptive_threads`）：

| 情況 | 採用的連線數 |
|---|---|
| 沒有基準值（沒量到 `bw1`） | 沿用 `base`（無證據不動） |
| 檔案太小／估計下載時間太短，不試探 | 沿用 `base`（尊重設定值） |
| 試探成功，吞吐 ≥ K 倍且延遲沒變差 | 用 `k`（`ADAPTIVE_PROBE_THREADS`） |
| 試探成功，但吞吐沒明顯變好 | **退回 1 條** |
| 試探失敗（連不上／逾時） | 沿用 `base` |

- `K = ADAPTIVE_GAIN = 1.35`。
- 延遲那一條是 **Vegas / FAST** 那一類的做法：加連線若讓連線延遲上升，代表
  只是把資料塞進同一個佇列，並沒有真的變快（`ADAPTIVE_LATENCY_TOLERANCE = 1.25`）。
  它只是**額外的否決權**；這條路上真正做決定的是吞吐那一條。
- 公平的比較是**牆鐘**：`T(n) = ttfb + total / bw_n`，取最小者。

### 8.2 經濟門檻（為什麼是 10 秒）

試探本身要付 `TTFB + 視窗 ≈ 2.5 s`。多開連線能省下的時間是 `est × (1 − 1/gain)`；
要打平得 `est > 2.5 × gain/(gain−1) ≈ 9.6 s`（`gain = 1.35`）。
所以 `ADAPTIVE_MIN_EST_SECONDS = 10.0`、`ADAPTIVE_MIN_BYTES = 16 MB`。

⇒ **快線不啟動**（34 MB 資產在 90 Mbps 上只要 3~4 秒，試探划不來）；
**慢線才啟動**（10 Mbps → est ≈ 28 s；100 KB/s → est ≈ 340 s）。
慢線正是這個 updater 存在的理由。

### 8.3 量測（`exp22` / `exp24` / `exp25`）

`exp22`（91 MB 資產、1.5 s 共同視窗、5 輪輪轉序、聚合吞吐）：

| 連線數 | 中位 Mbps | 相對 1 連線 |
|---|---|---|
| 1 | 236.3 | 1.00× |
| 2 | 234.9 | 0.99× |
| 4 | 240.5 | 1.02× |
| 8 | 317.4 | 1.34× |

⇒ 1→4 沒有聚合增益；只有 8 摸到第二個平台，且**落在雜訊內**
（每輪變異 1.7~2.4×）。

`exp24` / `exp25`（真網路端到端，把門檻暫時壓低以強制試探）：

```
NetRedirector（34 MB）  探針 4 條：吞吐 1.54x、延遲 0.34x → 採用
NetRedirector（34 MB）  探針 4 條：吞吐 0.98x、延遲 0.68x → 退回單連線
MultiSocks（92 MB）     探針 4 條：吞吐 1.34x、延遲 0.59x → 退回單連線
MultiSocks（92 MB）     探針 4 條：吞吐 1.71x、延遲 0.75x → 採用
```

⇒ **同一條路徑、相隔幾十秒，結論就從「採用」翻成「退回」。** 這是這個功能
最重要的已知限制（見 §9）。

### 8.4 開啟方式

預設關閉。開啟任一即可：

1. `updater.ADAPTIVE_CONCURRENCY = True`；
2. `config.json` 頂層加 `"adaptive_concurrency": true`
   （`_config_flag`，字串 `"true"/"yes"/"on"/"1"` 也算真；讀不到就回預設值，
   更新流程不因設定檔問題中斷）。

### 量測腳本的一個紀律

`exp9` 與 `exp10` 量同一個東西卻差 2.5 倍，原因是分母不同。
**任何「速度」數字在互相比較前，先確認分母是不是同一段時間。**
`exp9` 的 `t0 = min(t_first)` 是有意為之（要純穩定態），但它因此
**完全看不到 TTFB 成本** —— 那正是這次真正要解的東西。

第二條紀律：**A/B 要交錯，不要跟前一輪的歷史數字比。**
這條線的吞吐在 session 之間會漂移（同一天實測 175~319 Mbps），
拿上一輪當基線，量到的差異分不清是「改動」還是「線路」。
`exp14` 用 A,B,A,B,A,B 讓兩臂承受同一段線路狀態，結果兩臂區間**完全不重疊**
（A 最小 3.94 s > B 最大 2.70 s）—— 這種分離度才足以支撐結論。

第三條：**看「決策有沒有變」比看「數字準不準」更適合拿來調參。**
`exp17` 的判準不是速度準不準，而是「選出的路徑有沒有變」。
一個 30 倍差距的選擇，就算探針再保守也不該翻盤 —— 這讓「能不能縮預算」
變成一個**布林問題**，不必先解決這條線量不準的問題。

第四條：**量聚合吞吐時，檔案必須大於「視窗 × 線速」，而且要有位元組上限。**
`exp22` 第一版把 34 MB 資產配上 1.5 s 視窗：1 條連線在視窗內就把整個檔抓完，
於是「1 條」那三輪都讀到**一模一樣**的 182.8 Mbps（= 34.28 MB ÷ 1.5 s），
看起來像 8 條快 2.01 倍，其實是在量檔案大小。改用 91 MB 資產 + 每條連線
位元組上限 + 「有沒有撞到檔尾」的守門，才量到真數字（0 個無效樣本）。

第五條：**`requests.get()` 會阻塞到回應標頭到達才返回，所以「開一個牆鐘視窗」
不能寫在它前面。** `exp22` 第一版回傳全 0：視窗在 `get()` 返回前就過完了。
正解是先等所有連線都拿到首個 chunk（一個 semaphore/barrier），再一起開閘門、
共用同一個截止時間。

第六條：**curl 少了 `-L` 會回 302 且 0 bytes，但計時看起來完全正常。**
探 91 MB 資產時踩到，加上 `-sL` 才看到 `code=206 size=1024 ttfb=1.144`。
任何「curl 說很快但其實沒抓到東西」都先檢查這一條。
