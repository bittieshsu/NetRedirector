# NetRedirector v1.8.5

## 修正「代理靜默失效」：連上了，卻有一部分的流量沒走代理

這一版只有一個主題：**讓代理真的對每一個行程生效，而且失效的時候講得出來。**

v1.8.4 之前的引擎有三個各自獨立的缺陷，症狀全都是同一句話 ——
「代理明明開著、規則也對，但某些程式的流量就是直連出去了，而且畫面上毫無線索」。
三者成因完全不同，這一版逐一修掉。

> 如果你是從 v1.8.4 或更早的版本升上來，而且會在多使用者／遠端桌面的環境下用代理，這一版務必更新。

---

## 一、症狀

三種表現，其實是同一個問題的不同切面：

1. **遠端桌面（RDP）裡的程式不受代理影響**，主控台開的程式卻正常。
2. 連線看起來有走代理，但引擎**一直在把自己 relay 的封包降級成直連**。
3. 引擎日誌被同一種訊息灌爆 —— 實測某次 1865 行裡有 **1348 行**是它。

而且三者**完全靜默**：沒有任何提示、沒有任何錯誤，只能靠事後翻日誌。

## 二、三個根因

### (1) 引擎沒有 `SeDebugPrivilege`，讀不到其他帳號行程的名稱

引擎以提權身分執行，但要對 **RDP session 裡的行程**做
`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` 時一律回 `err=5`。

原因不是 session 隔離 —— 是**行程自己的 DACL**：行程的權限來自建立者權杖，
未提權的桌面只授與「自己」與 `SYSTEM`，所以提權的引擎反而開不了它。
**啟用 `SeDebugPrivilege` 之後，5/6 立刻可讀。**

拿不到行程名稱，引擎就無法比對任何「行程名稱規則」，只能套用
unknown-process action（預設 DIRECT）—— 連 catch-all 的 `* → PROXY` 都被繞過。

### (2) 行程查表的鍵不唯一，會讀到已關閉連線留下的列

`get_process_id_from_connection()` 只用 `(local_addr, local_port)` 查表。
但同一個鍵底下**合法地**有多列：LISTEN 加上它 accept 的連線、以及已關閉連線
留下的 `TIME_WAIT` 列 —— 而 **`TIME_WAIT` 列的 `dwOwningPid` 恆為 0**。

實測 400+ 個取樣**每一個都有重複鍵**。最關鍵的一筆：引擎自己 relay 埠
`192.168.1.200:33100` 的第一列**永遠是 `pid=0` 的 `TIME_WAIT`** ——
也就是說引擎一直在**重新分類自己 relay 的封包**，並把它們降級成直連。

### (3) 連線關閉後被當成新連線重新分類

舊版在**第一個** FIN/RST 就把連線追蹤的條目刪掉，而「新連線」分支又**沒有
SYN 旗標防護**。於是關閉之後的封包（用戶端最後一個 ACK、重送的 FIN、中繼自己的
FIN）全部無條目可匹配，被當成新連線重新分類。

此時 socket 已經沒了，TCP 控制區塊停在 `TIME_WAIT`、`dwOwningPid` 為 0 ——
查不到主人，於是套用 unknown-process action。**這就是日誌爆量的真正來源。**

## 三、修正

| # | 修正 | 做法 |
|---|---|---|
| 1 | 啟用 `SeDebugPrivilege` | `NetRedirector_Start()` 一啟動就啟用；部分成功要靠 `GetLastError() == ERROR_NOT_ALL_ASSIGNED (1300)` 判讀，**不是**回傳值 |
| 2 | 查表鍵改為完整 4-tuple | 第一趟比對完整 4-tuple，第二趟才放寬到「同一 local 端點的活列」，**兩趟都必須 `dwOwningPid != 0`**。IPv4 / IPv6 / UDP 一併處理 |
| 3 | 名稱查不到時不再短路 | 改以**空名稱繼續走規則比對** —— PID 規則與萬用字元規則仍生效，全都沒中才回 DIRECT（與原本的最壞情況相同） |
| 4 | 只有 SYN 能建立新連線 | 未追蹤的**非 SYN** 封包原樣重注入，不再被重新分類 |
| 5 | FIN/RST 不再立刻刪條目 | 改為標記「已關閉」，保留 **30 秒**寬限期（`TCP_CLOSING_GRACE_MS`），讓關閉期的封包仍走追蹤路徑，之後由 sweep 回收 |
| 6 | 規則判定為 BLOCK 的 flow 會被記住 | 因為守衛放行了未追蹤的非 SYN 封包，不記下來的話「規則改成 BLOCK 之前就建立」的連線會整條存活 |

**刻意保留不動**：引擎只在新連線的第一個封包（SYN）做一次規則判定。
這表示**引擎停止期間就建立的連線，不會被中途接管** —— 中途改寫一條已經直連出去的
連線只會把它弄壞。要讓它生效，重新建立連線即可。

## 四、這一版新增的「看得見」

過去這些問題之所以難查，是因為**引擎只把日誌轉發給介面、完全不落地寫檔**，
間歇性問題事後零證據。這一版一併補上：

- **`NetRedirector.engine.log`**（就在 DLL 旁邊，打包版即 `IntegratedApp.dist\`）：
  1 MB 輪替成 `.1`、每行 `fflush`、每秒上限 200 行（超出會補一行 `suppressed N`）。
  啟動時會 dump **預設路由 + 代理清單 + 規則清單**，事後對照不用再猜。
- **「無法歸因」的日誌現在同時印來源與目的端點**，否則分不出是用戶端流量、
  還是引擎自己在 relay 埠上的封包。
- **介面會提示權限問題**：拿不到 `SeDebugPrivilege` 時會提示使用者。
  只提示、不阻止啟動 —— PID 規則與萬用字元規則仍然有效。
- 高頻失敗路徑（查表、名稱查詢、握手）改為**節流輸出**，不再洗版。

## 已知行為（不是缺陷）

- **UDP 偶爾出現「could not be attributed」是正常的。** UDP 沒有 `TIME_WAIT`、
  沒有握手，端點列會隨 socket 關閉直接消失。實測元凶是 Windows 的 DNS Client
  （`Dnscache`，`svchost.exe`）：它每次查詢開一個新的臨時 socket、送出後很快關掉，
  引擎從佇列取出封包時列已經沒了。預設 DIRECT 下該封包原樣送出，與未開引擎相同。
- 對應的**降噪**（拉長 UDP 的節流視窗）留待後續版本。
